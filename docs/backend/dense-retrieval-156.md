# A10: real dense and hybrid retrieval

Implementation delivery, not a production verification claim. No provider calls, services, migrations, builds or tests were run for this delivery. Java/Maven and Java AST tooling are absent in the restored workspace.

## Architecture

Existing `/api/retrievals` remains the backward-compatible FULLTEXT endpoint. The new source-index operation path is separate from task-run invocations: it must not manufacture a run/step/action/connection-verification to satisfy an unrelated task-ledger FK. `index_item.embedding_operation_id` references the real `dense_operation`; the existing `embedding_invocation_id` FK remains unchanged and exclusive.

Real embeddings are obtained by `DenseEmbeddingGateway` from the exact deployment-approved HTTPS endpoint and credential reference/revision. Only a model authored through normal model configuration with protocol `EMBEDDINGS-1`, the request schema URI `urn:medical:embedding-request:1.0.0` and SHA256 of `embedding-request.schema.json` is eligible. The fixed model version, not a mutable model alias, is sent and must be echoed exactly. There are no generated/hash/random vectors and no fallback to simulation or FULLTEXT when embedding fails.

The vector backend is a bounded, exact SQL vector store, not Qdrant. `dense_index_vector` holds verified finite, nonzero vectors and their digests. The producer writes concrete `index_manifest`/`index_item`, checks complete cardinality, and publishes READY atomically. Model, configuration, price and parse lineage are registered. Query ranking does exact cosine; HYBRID additionally executes MySQL fulltext on the same authorized frozen chunks and uses deterministic RRF K=60, with stable source/parse/chunk ordering for ties. Max 10,000 chunks and 4,096 dimensions are admission ceilings, not performance guarantees; each embedding/query scan is additionally capped at 1,000,000 coordinates and each frozen exact manifest at 16 MiB.

## Authoring and use

All routes require authenticated application identity, `X-Schema-Version: 1.0.0`, and the current `X-Context-Revision`. POST authoring/build/search also require `Idempotency-Key`.

1. Author an external model revision normally. Supply existing approved credentials, model version, region, data policy, embedding protocol and request schema digest. Nothing in these endpoints provisions credentials or grants.
2. Supply an actual approved SOURCE original as price basis. Its JSON must contain profile `EMBEDDING_PRICE_1`, provider, model_version, currency, input_price_per_million, rounding `CEILING_8_DECIMAL_PLACES`, tokenizer_contract `UTF8_BYTES_UPPER_BOUND`. The original object is read and digest-verified, with current source/lineage authority. A caller-provided rate alone is insufficient. Chunk/locator input hashes are also compared against the existing immutable verified FULLTEXT or dense bootstrap manifest, not merely against mutable chunk rows. Providers without this tokenizer-bound contract require another implemented profile, not a guessed count.
3. POST `/api/dense-index-configurations` with schema_version, project_id, model_revision, mode (DENSE/HYBRID), dimension, maximum_chunks, maximum_input_bytes, input_price_per_million, price_basis {version_id,content_sha256}, reason. The revision is immutable; a new idempotency key creates a new version. GET `/api/dense-index-configurations/{revision}` reads it under current configuration authority.
4. POST `/api/dense-index-builds` with schema_version, config_revision, source {source_version,parse_version,snapshot_id,approval_revision,rights_revision,purpose}, budget_bases [enterprise basis,project basis]. The existing approved FULLTEXT scope provides bootstrap provenance; an unapproved or partially indexed source cannot be used to bypass source governance.
5. The returned PREPARED operation reserves both approved budgets. POST its `/api/dense-operations/{id}/execute` URL to consume the prepared operation. Dispatch state commits before network I/O. GET `/api/dense-operations/{id}` returns the state/result. Successful build returns an index_version.
6. POST `/api/dense-retrievals` with schema_version, config_revision, index_versions, query, limit, budget_bases, then consume/read its operation identically. Every index must use the exact same embedding configuration. Duplicate source chunks across index versions are rejected rather than double counted.

This is an explicit producer/consumer API, not an automatic background scheduler. The existing task research FULLTEXT caller is unchanged; adopting dense search in a task requires passing the resulting fixed index selections through that task's scope-authoring flow.

## Governance and durability

- Project/source read, fixed source approval/snapshot/parse/rights, classification, region/provider rights, source external processing, model.send, current model revision and approved credential are checked. Authority is rechecked immediately before dispatch and again before publication/read.
- Both enterprise/project approved budgets reserve actual fixed-price conservative upper bounds before send. Both settle from actual reported input tokens only after complete validated response. Missing usage or uncertain failure retains reservations and UNKNOWN, never invents zero cost or a receipt.
- Per-model embedding concurrency/request/token limits are serialized against the model revision; UNKNOWN remains an active uncertain call.
- Provider raw response is fsynced in a private deployment directory before parsing. A durable started marker prohibits duplicate sends. UNKNOWN/DISPATCHING retries read only the same original response; no response means unresolved UNKNOWN. No repair endpoint accepts caller-supplied vectors/receipts.
- Citations retain source version, parse, index, chunk, approval, rights, quote hash, title and exact locator. Unicode excerpt truncation is explicit. Reads recheck current source eligibility and stored index completeness rather than returning cached authority.
- Gateway readers/writers hold an exclusive journal file lock; purge cannot attest absence while an original-response writer is alive. Source purge invokes `DenseRetrievalRetention` under the existing deletion worker's lease/current purge authority. It withdraws dense manifests, erases vectors, copied request/chunk/citation material and gateway original files, verifies absence, and prevents confirmation during a potentially in-flight send. Known never-dispatched preparations release reservations; uncertain costs do not. Ordinary revocation/recycle immediately blocks future sends/reads even before purge.
