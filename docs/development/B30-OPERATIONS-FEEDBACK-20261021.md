## Read-only metrics

GET /api/business-operations/metrics requires schema/context headers and explicit from, to; project_id and actor_id are optional. Omitting project_id requires current ENTERPRISE report.read and computes enterprise groups, never a union of guessed project permissions. The interval is half-open UTC, at most 93 days, and cannot extend beyond the database observation time. Current report.read / BUSINESS_OPERATIONS scope authority is mandatory. Summary-only is the default (include_records=false), respecting PRD867 report viewers without raw-source permission. Explicit include_records=true additionally requires each source task/document read authority. Missing authority rejects the report, not a secretly partial denominator. Tenants are explicit in every SQL join and current tenant transaction admission locks identity/governance watermarks.

The report returns its tenant, project, actor filter, interval, database observation time, auth/governance epochs, named metric revision, cohort definitions and exclusions. Exact source IDs are included only with separately authorized include_records=true. This is a live observed cohort, not a claim of an immutable historical snapshot. Each source query is capped at 2000 rows; overflow fails CONTEXT_LIMIT rather than truncating a numerator. Output is capped at 8 MB.

- Usage: registered task model invocations, joined through actual task_run. Reservations, failed/unknown/cancelled calls remain visible; a registered invocation is not mislabeled a successful provider call. System jobs and simulation runs are excluded explicitly.
- Cost: immutable formal_invocation_accounting receipts are hash/pin checked and cross-bound to invocation_receipt provider capture and invocation settlement state. Amount/token sums include only settled evidence. Disputed, missing, pending or incomplete evidence remains unknown; total_amount is null when any cost is unknown. Currency groups never mix. Raw task/run/revision/invocation/receipt IDs require include_records=true and source authorization.
- Adoption: distinct created-candidate cohort, with a real candidate_adoption joined to a completed operation. Adoption is observed as of report read, not necessarily within the creation interval. Combined and PLAN/DOCUMENT groups expose numerator and denominator. No candidate status string alone counts as adoption. With no actual adoption record the rate stays null/INSUFFICIENT_EVIDENCE, even when candidates exist (EVAL-08).
- Return: formal review decisions in the decision interval; numerator is RETURN, denominator all formal decisions. Historical invalidated decisions remain historical decisions, explicitly labeled. Independent document_revision_return entries are separate counts/raw references, never silently mixed into the formal-review denominator.
- Zero denominator gives null rate and INSUFFICIENT_EVIDENCE. Quality improvement and time saving remain INSUFFICIENT_EVIDENCE, not inferred from invocation success. These are explicit operational cohort definitions; no unprovided E02 customer acceptance threshold is invented.

## Feedback

POST /api/business-operations/feedback accepts project_id, target_version (actual formal Agent candidate) and reason. POST /api/business-operations/feedback/{id}/transitions accepts expected_revision, state, reason, revision_version, acceptance_id, release_id (the three reference fields are explicit nullable fields). GET the feedback ID returns immutable events. GET the collection with project_id and optional after_id provides current managed-feedback receipts in 100-item keyset pages; legacy feedback without managed events is explicitly outside this collection. Write requests require Idempotency-Key. Duplicate actor/key/body returns the exact original receipt under current feedback authority; changed content conflicts.

Required current grants are feedback.create/read/manage with purpose BUSINESS_OPERATIONS, plus actual configuration/publication read authorities. New records inherit the actual target classification. Revision linking requires a different real authored candidate in the same project, created after the feedback and with the same classification. This is an explicit human-proposed replacement link; it is not an invented automatic source-code ancestry claim.

OPEN → REVIEWED → REVISION_LINKED → EVALUATED → PUBLISHED → CLOSED. OPEN/REVIEWED may instead end REJECTED. No milestone skips or terminal reopens. EVALUATED consumes actual accepted evaluation/candidate metadata; PUBLISHED and CLOSED independently prepare/read physical publication evidence via AgentPublicationAuthority, revalidate current acceptance/evaluation/dependencies/scope, and require the exact revised candidate and acceptance/release join. Missing deployment/object/provider evidence remains DEPENDENCY_UNAVAILABLE or the underlying error. A human closing feedback does not constitute clinical approval.

Migration 172 adds operations_feedback_event with schema/hash/creator/time/classification metadata, tenant/entity FKs, per-feedback revision and per-actor idempotency uniqueness, immutable update/delete triggers and managed-feedback head transition guard. Events, feedback head CAS, audit and outbox are one tenant transaction. Existing unmanaged legacy feedback rows are not rewritten.

Agent feedback lookup requires an existing operations_feedback_event, not merely a matching legacy feedback ID. SOURCE/RULE feedback uses the separate 177 knowledge_feedback_origin/event domain. Each head trigger is conditional on its own domain sidecar; domain attachment guards prevent a feedback head acquiring both kinds of history.

## Required-scope extension and permission-authoring proof

PRD659 explicitly requires category/product/stage/document/role filtering; PRD880 requires enterprise aggregation; PRD800 requires SOURCE/RULE feedback (separate KnowledgeFeedback* implementation, migration 177). These are not optional enhancements.

The metrics query now supports device_category, product_type, stage, document_type and role_version. Each historical row resolves task_revision → pinned profile_revision/template_version. Project profile attributes and authority_refs are hash-checked against both the profile and version registry and validated by the existing ProjectSchema. Current profile values are never substituted for task-time values. UNKNOWN/missing/unsupported-valued attributes are excluded when a filter is requested, with explicit per-reason counts. Dimension groups retain null UNKNOWN values and independent per-group denominators/currency totals.

Because project attributes are user-authored keys, there is no invented global category taxonomy. Deployment must explicitly bind medical.business-operations.device-category-key, product-type-key and stage-key to the actual authorized reportable profile keys. Query *_key fields, when supplied, must match those server bindings; arbitrary attribute extraction is denied. An unconfigured requested dimension returns DEPENDENCY_UNAVAILABLE. Omitted value filters use configured dimensions for grouping, with unknowns kept null. role_version means immutable producing run_step.role_version, not a person's current role; a document revision with no original producing adoption link remains UNKNOWN. This prevents historical reassignment and inference from current membership.

GET /api/business-operations/metrics.csv requires report.export in addition to report.read and the same selected-source grants for include_records=true. CSV preserves filters, observation watermarks, formulas/denominators, unknowns and source references (only when authorized). Amount/count columns contain validated numeric literals; untrusted text is CSV-quoted and neutralized for formula prefixes after whitespace/control/format characters. No export or provider was executed in this implementation session.

Normal grant authoring is already supported, not an unreachable service-only permission: permission-decisions.schema.json Action (line9) permits scoped lowercase action names, Condition.purposes (line37) accepts BUSINESS_OPERATIONS and Kind (line10) permits PROJECT/ENTERPRISE. PermissionSchema.request validates exact project/enterprise identities. PermissionDecisionService GRANT (lines86–96) persists the submitted action and condition after authorized delegation; verifyResources resolves actual ownership. PermissionMapper.resourceOwner lines70–71 resolves actual tenant/project rows. PermissionAuthority.findGovernance requires explicit delegated actions, scope, validity and purpose, so none of these endpoints self-grants permissions. Existing administrators must have the applicable bounded delegation before using /api/permission-decisions.
