# RN-01 run-creation boundary, 2026-10-16

## Status

Partial implementation, not a runnable production execution feature. RN-05 continuation remains unimplemented. No release approval, evaluation result, execution success, model connection or operational retention policy was created by this change.

The code provides the real RN-01 HTTP, validation and transactional persistence path. Its final C06 admission consumer is deliberately absent, so an otherwise eligible request fails with `DEPENDENCY_UNAVAILABLE` before any run, principal, command, operation or audit is written. A completed evaluation row alone is not accepted as proof that evaluation gates passed.

## Implemented

- `POST /api/tasks/{taskId}/runs`, application session identity, CSRF through the existing security chain, single schema/context/idempotency headers, no query-string authority, closed input schema.
- Current `task.read` and `task.run` authorization. Current READY task, exact task/plan/snapshot pins, task-head revision CAS, confirmed plan, currently eligible template/rules/formal source versions and section owners.
- Current PUBLISHED release metadata, COMPLETED evaluation prerequisite and current release audience/scope. These are prerequisites, not complete C06 approval.
- Current budget approval revision, ownership/content/schema verification, budget read permission, currency, deadline, spent plus reserved money/tokens/calls. The acceptance check does not reserve or charge money; dispatch still requires the existing per-action reservation rules.
- Single active-run slot. RN-01 is limited to a task's first run; any historical attempt must use the future RN-05 predecessor/unknown-invocation flow.
- One enterprise transaction for task-head CAS, execution registry, QUEUED task run, run principal, active-run slot, empty durable event stream, PROCESSING operation, audit and `run.start.requested` Outbox command. Task remains READY until a real first-step admission makes it RUNNING.
- Complete replay bytes must pass their published schema and bind all fixed identities. Scope and principal manifests use the existing `RunTokenAuthoritySchema` and current permissions. Persistence is re-read before committing; current release/source/budget/permissions and C06 proof are checked again.
- Exact same-key retry recovers the original 202 receipt with current scope authorization; changed body/task conflicts. Stored command digest, fixed task versions, replay and principal identities are checked. Retrying does not enqueue a second run.
- Acceptance is always QUEUED/PROCESSING, with no started/ended timestamps and no synthetic steps, workflow start or paid-provider call.

## Required next consumers

1. Implement the common C06 execution eligibility consumer behind `RunCreateAdmission.require`. It must check actual evaluation gate acceptance, every current release dependency/runtime artifact, source-scope intersection, retrieval/network approval and model-connection/version eligibility. Share appropriate primitives with the existing `TaskCreateReleaseAdmission` and `TaskPlanReleaseAdmission` consumers rather than treating their current absence as a usable feature.
2. Publish the complete replay contract as `urn:medical:replay-manifest:1.0.0` with its real catalogue checksum. `Verified.replayManifest()` returns the schema-bound complete content. The service requires tenant/project/initiator/task/run/release and task/plan/snapshot/budget bindings; the published contract and C06 consumer must cover the remaining LLD Data §6.3 runtime/model/tokenizer/parameter/artifact/schema/locale/input/output details. No placeholder schema is registered.
3. Supply least-privilege scope/principal manifests and a real approved event-stream retention version from that same consumer. Scope identity is validated with `RunTokenAuthoritySchema`; the referenced retention version must exist in the correct enterprise/project. The consumer remains responsible for its category, approval and effective status. The existing SOURCE-only retention table is not substituted as RUN retention.
4. Consume `run.start.requested` idempotently through the C04/C11 workflow boundary. The command carries run/principal/operation IDs, stable tenant/run workflow ID, replay schema and content hashes, immutable request/permission decision and a command hash. Recheck admission, start only the authorized workflow, create actual step records, and advance operation/run/task state from actual acknowledgements. A queued row is not proof that a worker is available.
5. Implement RN-05 with predecessor dispatch closure, unknown invocation reconciliation, same-input result reuse, fixed/current version semantics, cumulative budget and explicit successor links. RN-01 does not act as a retry bypass.

## Validation

`RunCreateBoundaryTest`: nine deterministic tests cover strict request and receipt schemas, unsigned revision limits, pinned version/state checks, canonical idempotency identity, absent-C06 denial, deadline and cumulative reservation exhaustion, mapper registration/current-subject enforcement, tenant SQL rewriting, queued-only writes and closed HTTP headers/query behavior. These tests need no live secrets or database.

The parent build ran the nine tests successfully before the final mapper identity/tenant-rewrite additions; those final additions require the selected test to be rerun. No admitted transaction/database integration or live HTTP success path has been claimed. The missing C06 provider, published replay contract and stream-retention approval prevent a genuine successful admission fixture at this stage.
