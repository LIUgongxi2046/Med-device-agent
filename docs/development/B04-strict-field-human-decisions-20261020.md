# B04 DC05 saved strict-field decisions

Implementation choice, additive contract, not a claim that the previous DC05 row already defined a closed API. `backend-design/strict-field-human.schema.json` is mirrored into persistence resources. Request and receipt/history schemas reject unknown properties, duplicate JSON keys and trailing input. Routes use normal human identity and document-scoped field.confirm permission; worker admission cannot substitute for a human.

## Actual closure

- Read saved DOCUMENT bytes through DocumentReadService; bind exact field, node, immutable body hash, optional row and physical field_value projection. Non-null row requires a real TABLE row, not a supplied row identifier alone.
- Read actual N07 findings+coverage through B07 ProfessionalCheckService, current rule manifest/claims, sources, input and watermarks. A field confirmation needs real supported/located/access-allowed field claim and all relevant node rules PASS. UNKNOWN/FAIL/BLOCKED cannot be overridden by a human.
- CONFIRM requires a physical N03 output in this saved document's dependency closure. Verify output registration, original audit, rule set and actual object bytes. Bind N03 input to task/plan/snapshot/template, typed target and independent current target approval; bind exact field-definition/node/row, candidate raw/decimal/unit and original source value, candidate model/condition literal and IDs, current policy and source-context approvals, and method requirements. A TASK check is not reused just because its field UUID matches. Ambiguous multi-model body representation is rejected, not guessed.
- Missing N03 requirement IDs, UNKNOWN result, non-MATCH, missing methods, missing method source evidence or stale input prevent CONFIRM. FIELD_ONLY does not invent method requirements; METHOD coverage comes from the real approved typed requirement inventory.
- NOT_APPLICABLE requires the current template FIELD machine condition to be NOT_APPLICABLE with an actual approved rule reference, plus current relevant N07 rules NOT_APPLICABLE. A human template override, free-text rationale or machine failure does not authorize it.
- REQUEST_EVIDENCE saves an actual nonblank question assigned to the requesting human and exposes a normal read queue. It never writes evidence_link, source evidence or a support success. A later field head makes its old question visibly SUPERSEDED, preserving its original record.

## Persistence and consumers

Migration 135 adds immutable decisions, a per-document/field/row CAS head, and question records, with standard metadata and real FKs to field_value/document_head/document_revision_meta/member/operation/version registry. The enclosing EnterpriseAccess transaction writes registry, operation, immutable decision, CAS, audit, outbox and existing review invalidations atomically. Same actor/key/body recovers the original receipt before current baseline/CAS reexecution. Different body or document conflicts. Original receipts do not imply current validity.

Current reads and formal-review consumers never trust mutable FieldValue.status. `StrictFieldHumanService.prepareConfirmed(subject, context, FixedRead)` physically prepares latest saved field decisions outside the transaction; its `Confirmed.requireCurrent(admission)` rechecks exact state in the caller's transaction, while `witness()` returns actual immutable receipts. All actual field rows must have a current CONFIRM/NOT_APPLICABLE head. Permission/governance epochs, current body, N07/N03, source approvals and exact baseline are fail-closed. Linked shared fact usages also re-enter B05 SharedFactConsumptionAuthority for new confirmations rather than promoting historical readable facts. No fallback to older decisions. The only accepted N07 watermark transition is the genuine B08 current full batch that proves the original check receipt and exact evidence +1 with unchanged issues through `requireValidForHumanEvidence`; the affected field human support must also match its applicability. Other stale branches remain rejected, and a later ordinary document-head revision alone is not a semantic invalidation.
