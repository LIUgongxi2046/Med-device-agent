# DC-04 additive shared fact contract v1

Implementation contract, not a reinterpretation of FieldValue or legacy status values.

* `FactProposal` is an immutable, separately stored canonical content revision. It is never registered as SHARED_FACT. Its current head uses CAS. The proposal pins an actual fixed document revision and nonempty original evidence links. Content carries `fact_class`, verbatim `raw_value`, nullable exact decimal string and unit, and explicit `model_scope` and `condition_scope`. SCOPED models and one SCOPED condition are derived from an independently approved original-source context, bound to the actual fixed document task/plan/template/snapshot and a declared original evidence link. A client cannot supply arbitrary model/condition UUIDs. NOT_APPLICABLE remains explicit; no unresolved context is silently flattened.
* Policy revisions are explicitly approved with current project `fact.policy.approve` / `SHARED_FACT_GOVERNANCE` authorization. No default policy exists. `HUMAN_ONLY` explicitly declares that this class requires no deterministic checks; `EXACT_CHECKS` declares required rule-version IDs and remains fail-closed until an exact fact-input check consumer exists. Document/N05/N07 checks are not fact approval.
* Human verification is append-only SUPPORTS, CONFLICT or NEEDS_EVIDENCE, with nonempty reason. Verification reopens and hashes real original and parsed evidence, checks exact locator/quote and current source authorization. The verifier must differ from the proposal author. Accessible evidence alone does not assert support: SUPPORTS is the authenticated human's explicit substantive decision. Decisions bind the proposal hash, current policy, full citation proof, fixed body digest and current authorization witness.
* Independent adoption requires `fact.adopt`, a SUPPORTS decision, current policy, exact current proposal, current physical evidence proof, and an adopter distinct from author and verifier. Only this transaction creates an immutable SHARED_FACT registry/domain row, adoption record and current fact head. `verifier_id` is the actual verifier, never the adopter/requester by default.
* Proposed replacement revisions remain possible; adoption over an existing current fact is blocked pending B06's exact complete impact/invalidation capability. A direct-use list cannot unlock it. Existing signed bytes are untouched.
* New document-body consumption requires the adoption sidecar, current fact head and current policy; original dependency authorization remains mandatory. Legacy versions without a sidecar remain readable using the original existing rights checks, but cannot silently acquire eligibility for NEW consumption. No existing row/status is rewritten and no historical decisions are synthesized. Rollout needs an actual deployed inventory and explicit reviewed compatibility decisions before any exception for new legacy usage.
* API requests use schema/context headers and original idempotency keys. Recovery matches exact actor/project/action/request hash and returns the original immutable receipt under current read authorization, not a new approval. Mutable heads and all immutable rows have tenant/project owner FKs and metadata. New policies/heads advance governance epoch. No runtime facts or policy seed is supplied.

Routes: POST /api/projects/{project}/shared-facts/policies; POST /api/projects/{project}/shared-facts/proposals; GET /api/projects/{project}/shared-facts/proposals/{id}; POST .../proposals/{id}/verifications; POST .../proposals/{id}/adoptions. Policy configuration is an explicit approval endpoint, not a boolean flag on a proposal.

Deferred verification: schema rejection/duplicate fields; empty or missing policy; false support vs accessible evidence; independent actors; current source revocation/quote drift; stale policy/head CAS; immutable retries after write revocation; legacy read/new-use separation; transaction rollback; replacement impact gap; cross-tenant/project; foreign-key metadata; adoption lineage and current source authority. No tests, database execution or runtime validation performed in this development stage.

## Exact fact-check implementation (supersedes the initial capability gap above)

The implementation now adds explicitly approved immutable `shared_fact_check_rule` revisions, authored by POST `/rules` under `fact.rule.approve`. These are fact-specific rules, not Boolean applicability rules or field-policy aliases. Each rule binds one fact class, `TEXT_EXACT` or `DECIMAL_EXACT`, explicit unitless scope and optional required exact decimal scale. Policy approval resolves every referenced real rule and rejects a class mismatch. No default rule or PASS is created.

POST `/proposals/{id}/checks` under `fact.check` reopens the actual original and parsed source objects and retrieves their verified located literal. TEXT_EXACT compares the entire literal byte-for-byte to the proposed raw value for every declared evidence link. DECIMAL_EXACT additionally runs the existing lexical decimal parser on the actual original-derived literal and checks exact declared decimal/scale. Non-unitless automated rules are rejected until a separate authoritative unit binding exists. This bounded numerical operator does not imply arbitrary prose or clinical validation. Model/condition scope is separately verified from the approved typed source context; optional value_evidence_link_ids must be a nonempty subset of the full evidence set so context citations are not falsely treated as numerical value literals.

The immutable check record binds exact proposal content digest, current approved policy, every real rule revision/digest, actual evidence/locator/quote/processing proof, fixed body digest, result and authenticated actor/grant. PASS and FAIL are persisted as calculated, never client supplied. Adoption requires a genuine matching PASS baseline for EXACT_CHECKS, reopens current evidence again, re-evaluates the exact checks and validates complete nonempty rule coverage before creating a fact. The new-use gate verifies this exact ledger; document/N05/N07 checking still never substitutes.

B06 owns the injected `SharedFactReplacementImpact` proof and the complete graph/decisions/invalidation operation. The static failclosed placeholder is being replaced by that worker; B05 calls it inside its admission transaction before replacement adoption and head CAS. A replacement is not complete while B06 is unavailable. Proposal registry rows have the distinct `SHARED_FACT_PROPOSAL` kind only to support real change-proposal foreign keys; they are not consumable SHARED_FACTs.

Final development handoff: the B05 production-only 15-source Java 17 diagnostic slice passed before the B06 seam gained its service dependency. A subsequent final slice is pending B06's new VersionChangeImpactService (the only reported missing symbol); no full build, test, database migration, runtime, provider or network execution was performed. Deferred test source `SharedFactExactCheckTest` covers actual-literal vs hash-only proof and exact decimal/scale rejection. The adoption consumer requires the latest verification for the current proposal/policy; a later conflict or needs-evidence decision cannot be bypassed by selecting an older SUPPORTS ID. Equal-time competing decisions fail closed. Legacy fact-key collisions without a reviewed current head also fail closed rather than becoming implicit replacements.
