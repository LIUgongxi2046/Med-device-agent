# A3 N01 PLAN_DRAFT: proposed closed execution slice

Status: design proposal plus isolated pure policy; A3 is NOT complete. No deployment, actual job, provider result, artifact receipt, independent server check or human decision is claimed. The new policy is deliberately not a Spring bean and is not exposed as a completion authority.

## Existing contracts and actual consumers

- `LLD-Agent.md` § professional execution ordering: N01 runs as `SYSTEM_JOB`, `job_type=PLAN_DRAFT`, with fixed task revision and scope manifest. TASK plan fields are null; task linkage belongs in the job input manifest. Only after human TK-04 does TASK execution have a non-null fixed plan.
- `agent-design/artifacts.schema.json#/$defs/PlanCandidate`: template/profile pins, complete requirement node list, sections, questions and pending condition IDs. Sections own node IDs; research question requirements must be owned by their section under `TaskPlanPolicy`. Do not reinterpret requirement IDs as arbitrary field IDs.
- `agent-design/tool-inputs.schema.json#/$defs/PlanArgs`: AT-10 accepts only `plan_artifact_id`. It does not authorize inline bytes, a user decision, an arbitrary template, or a caller-supplied receipt.
- `TaskPlanService.save` (TK-03) already writes an actual draft with immutable registered version, source/owner/template/rule checks, head CAS, lineage, audit/outbox, original-operation recovery and response verification.
- `TaskPlanReturnService` (TK-04) already supports explicit human confirmation/return, exact baseline and current publication validation, immutable decision receipts and original recovery. `TaskPlanConfirmationStore` creates the fixed confirmed task/plan revisions. `TaskPlanService.execution` requires that actual confirmed plan before TASK launch.
- `FormalEvaluationPlanExpansion` and `FormalEvaluationPlanPreparationAuthority` are evaluation preparation, explicitly not runnable professional results. They must not be used as an N01 execution proof.
- `FormalWorkerAccess` currently permits SYSTEM_JOB only for exact MODEL_VERIFICATION/CONFIGURATION. `RunTokenAuthority` has a similarly dedicated verification branch. A task-only host/input capability cannot be relabeled N01 or allowed to carry a null plan by weakening validation.

## Coverage without changing PlanCandidate 1.0.0

The existing immutable template pin transitively fixes every field, attachment and repeat definition. Each definition has a node owner, and existing plan validation requires each template node to be covered exactly once by a section. Consequently field/attachment/repeat coverage can be deterministically reconstructed and checked against that immutable template without extending the public candidate contract.

`TaskPlanDraftCandidatePolicy` now performs that expansion/inspection, deriving stable section IDs from tenant/run/task revision/template version+digest/profile/node. It preserves template ordering and nodes even when not applicable or applicability is unknown. Proposed dependencies and question dependencies are checked using the existing DAG validator. Model-assisted nodes without research questions remain missing, as do owners and completion rules. Template condition UNKNOWN and actual template missing-requirement IDs remain visible. Verification rules are never automatically promoted to completion rules, hierarchy never becomes an invented research dependency, and no owner/method is guessed.

Coverage and missing-items in this local record are diagnostic data, not a registration, authoritative admission, professional check or completion certificate. Source/material missing-items additionally come from the genuine fixed task input and scope manifest, not from generated prose. Current template/profile/source permissions must still be established by a producer and rechecked by a consumer.

## Proposed closed additive contract family

Add one local versioned schema `task-plan-draft.schema.json` with a new namespace rather than mutating frozen shared artifact/tool schemas. Every object is closed, every identity/digest is bound, and nonempty bounded collections have explicit maxima. This proposal needs root review before implementation.

1. Start request: schema version; task ID; exact expected task head revision and task revision; fixed template/profile/release bases; execution-policy basis; enterprise and parent budget bases; requested maximum cost/token/timeout envelope; reason. Source snapshot and source purpose derive from the actual task input, never caller-selected widening. Public operation/path must be explicitly approved in the interface design before exposing a controller.
2. Admission: tenant/project/actor/context; operation/request digest; run/principal/step/action IDs; literal SYSTEM_JOB/PLAN_DRAFT/N01; task revision and task input/source-snapshot digests; template/profile/release/policy/model/prompt/role/skill/knowledge pins; scope/principal/config/rule manifest IDs and digests; budget reservation and parent-budget bindings; output schema pin; concrete input artifact and receipt digest. No plan revision is required or fabricated. It is persisted by a private-constructor authority, not accepted as caller proof.
3. Candidate registration receipt: original job/input/step/action/lease identity; PLAN_CANDIDATE artifact/object version/content and schema digests; original write intent and immutable storage GET proof; all source/knowledge/dependency access-set pins; registration/audit/outbox identity. A UUID or an existing artifact registration alone is insufficient.
4. AT-10 receipt: session/call/action/run/step/input/lease and request digest; original candidate registration receipt digest; deterministic coverage/missing-items manifest digest; target task revision; waiting-item identity. Status is SAVED_PENDING_REVIEW or WAITING_INPUT, never CONFIRMED. Same call recovers exactly its original receipt and cannot point to a different artifact.
5. Independent server check: separate check identity and implementation/version, independently reread actual saved candidate/object receipt, fixed source/template/profile/rule/knowledge pins, complete scope and coverage, result and unresolved issues, original audit/outbox. This is the LLD backend domain validation, not a newly invented N05/model checker. Local structural validation is only one input: actual current template/profile/source/rule/owner checks and genuine saved bytes are mandatory; source/material UNKNOWN remains unresolved.
6. Candidate-to-draft adoption binding: human-selected candidate identity, registration+AT-10+current check receipts, expected task and plan head, TK-03 original operation and resulting draft hash. The resulting draft content must exactly equal the original candidate. Subsequent manual changes make a new draft and require rechecking; they cannot inherit the old candidate check. A new sidecar relation binds the actual draft to this evidence without adding fields to PlanCandidate.

## Producer/consumer implementation order and ownership seams

A. `TaskPlanDraftAdmission`, `TaskPlanDraftJobs`, `TaskPlanDraftLedger`: use EnterpriseAccess, TaskService.fixedTask, TaskPlanService.sourceProof, TemplateApplicabilityService/ProjectService fixed profile, current publication/execution policy and budget authorities. Produce QUEUED job, execution registry, scoped principal, budget reservation and outbox in one transaction. Out-of-transaction original object I/O uses existing exact write-intent/conditional-PUT/full-GET transport pattern. Real launcher acceptance performs QUEUED→RUNNING; no eager successful job.

B. `TaskPlanDraftInputAuthority` and `TaskPlanDraftRuntimeAdapter`: a dedicated pre-plan capability carrying actual fixed inputs. Reuse F1/F2 exact context/session/recovery primitives only where they have no TASK graph or plan assumption. Do not reuse N02 TaskNodeInputAuthority by inventing a plan/section/question. N01 Planner tool allowlist is AT-03/04/08/10; current allowed knowledge content and external-send permissions remain independently checked. Model may propose questions/dependencies; complete directory expansion remains deterministic.

C. `TaskPlanDraftRegistration`, `TaskPlanDraftToolBridge`, `TaskPlanDraftReceipts`: AT-10 selects only a physically saved candidate from the exact job/input/session/action lineage. Validate full candidate and source access set before saving a real receipt and wait item. No AT-10 path reaches plan.confirm. Lost response reads the original request/intent/registration/receipt instead of generating or uploading anew. Unknown PUT preserves the original key.

D. `TaskPlanDraftCheckAuthority` and `TaskPlanDraftAdoptionService`: read the actual saved bytes and current independent check; perform human-triggered adoption into the existing TK-03 store and persist the binding atomically. Existing TK-04 confirmation/return remains the human decision entry. Introduce one narrowly scoped optional candidate-evidence guard in TaskPlanConfirmationStore: if a draft has an A3 origin binding, current check must match the complete candidate/draft baseline. Absence of the guard for an A3-origin draft fails closed; legacy human-authored drafts retain current behavior. Include that evidence in the existing confirmation dependency hash/baseline, not a silent global bypass. Rejection does not reopen a terminal run; it creates pending rework/new job when explicitly requested.

E. `FormalWorkerAccess` and `RunTokenAuthority`: separate exact PLAN_DRAFT authority hook that reloads its immutable admission and current bounded job/run/step/lease/budget/context proofs. Keep existing TASK and MODEL_VERIFICATION branches unchanged. Do not use a generic job_type IN list or permit arbitrary SYSTEM_JOB. Job token cannot acquire plan.confirm or any capability outside its admitted manifest. These two shared files require root coordination; A1/A2/B01-owned files remain untouched.

- RN01 accepts only the actual resulting confirmed task/plan revision, never candidate or original PLAN_DRAFT job.

Remaining deployment/database/provider/UDS checks continue to belong to B31 and are not replaced by these unit tests.

## Implementation checkpoint (2026-10-20, code in progress)

The private producer now derives N01 fixed output authority from the genuine published role, approved execution policy and exact AT10/plan.write scope. It does not reuse N02 or invent an additional human producer approval. It limits this implementation to one input, one exact model input, one provider capture, one model result and one candidate, with one paid model invocation. Candidate size is at most 1 MiB and exact-input/model-result/capture at most 2 MiB, further bounded by actual runtime limits. Immutable kind/run uniqueness enforces cardinality.

Admission resolves the unique actual approved RuntimeRetentionAuthority RUN_CREATION policy, freezes revision/hash/terms and real authorization evidence, and includes the policy in exact dependency_versions. Retention is preservation, never an invented production deadline. The producer's nullable cutoff is the earliest actual policy/grant/source deadline. Every new production checks current authority. Original authenticated provider facts may still be recorded after expiry or revocation, using the original actual dispatch, immutable commitment and original retention; this confers no new send, read or candidate-producing authority.

Human start must physically read the actual role-selected prompt/profile packages before queueing. TaskPlanDraftPackagePreflight produces private read receipts. Admission.missingPackageSelections returns precise fixed-scope selection requirements; Admission.withPackages freezes those receipts only after current recheck and complete selected source closure. Pure configuration packages need no fabricated source leaf. Jobs.queued rejects missing preflight evidence.

Candidate original reading now checks actual input/intent/attempt/registration/audit/outbox, supervisor closure, settled original model result and deterministic normalization before exact-version object GET. Human current permissions are independent of the historical initiator. OriginGuard checks actual base-version ancestry and requires a new current independent completeness check for the exact draft before TK04. Existing manual drafts with no A3 ancestry remain unchanged.

Public start/read/adoption service wiring and original-operation recovery are now implemented. The business slice is code complete pending the final lightweight interface compilation and coordinated runtime handoff; integration and regression tests remain deferred. Public GET follows existing task-read permissions, while start/adoption explicitly require plan.write. Same-input independent checks reuse a genuine stable receipt after current reread so preview and TK04 baseline CAS are compatible. No mock provider outcome, approval or deployment evidence has been substituted.
