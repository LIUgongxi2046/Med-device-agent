# B10 signing implementation handoff

Implemented software only. No actual document has been signed, no provider contacted, no agreement accepted, no database/runtime started, no tests/full build run. Narrow production-source compilation is the only execution check. User requested development before tests.

## Normal deployment and human workflow

- Default off: `medical.signing.enabled` must be explicitly true. It requires existing real OIDC application identity, `ClientRegistrationRepository`, genuine N07/B07, B08/B04/B09 review services, B06 impact gate, and a separately managed 32-byte `medical.signing.pkce-encryption-key-base64`. No permissive fallback or sample success provider.
- Operator configures a real Spring OIDC authorization-code registration using HTTPS issuer, authorization/token/JWK endpoints, client ID and provider-managed secret if confidential. Only RS256 and `client_secret_basic` or public-client `none` are supported. The provider must pre-register the exact HTTPS `/api/signing/oidc/callback` redirect. This dedicated callback extends ID-02 rather than replacing the ordinary login callback. It retains and verifies the existing user/session/issuer/subject; it cannot create a session or change identity.
- Authorized project policy author invokes `POST signing-policies` with the real registration reference, required ACR/AMR, bounded challenge/receipt/auth-age limits, document-author separation (mandatory), and explicit reviewer separation policy. A different authorized person approves the immutable policy through `signing-policy-approvals`, using an exact expected-current-policy CAS. No manually seeded database rows are a supported integration route.
- Required grants: project `signing.policy.write` and `signing.policy.approve`, purpose `DOCUMENT_SIGNING_POLICY`; document `document.sign`, purpose `DOCUMENT_SIGNING`, alongside existing actual plan/template/source/document read permissions. Session and worker-authority boundaries remain enforced.
- RV-08 computes current true review/strict-field/professional checks, plan/template/source permissions, author/reviewer separation, no unresolved annotations, B06 resolved impact state, body hash, dependency manifest and all watermarks. It returns pins for the signature input, never a signature.
- BX-14 creates a user/session/context/content/purpose/policy/provider-bound challenge. PKCE verifier is AES-256-GCM encrypted with challenge AAD; state/nonce are stored as hashes. Maximum eight live challenges per user. Provider request forces fresh login, max_age=0, requested ACR and S256 PKCE.
- Callback consumes the code-exchange attempt once before network work. It uses the actual token endpoint and cryptographically validates RS256, issuer, audience/azp, expiration, not-before, auth_time, iat, nonce, current subject and approved ACR/AMR. Only sanitized evidence hashes/claims are persisted, never the code or tokens. Uncertain exchange is not retried. A lost successful callback response can be recovered through the current-session-only challenge status route.
- BX-15 accepts only an existing server callback receipt. Expiry is capped by both approved receipt lifetime and authenticated-at maximum age. RV-09 requires explicit human_confirmation and recomputes all gates within the same EnterpriseAccess transaction, then appends the signature, original signed body bytes, immutable manifest and operation/audit/outbox evidence, consumes the one-use receipt, and CAS advances document/task to SIGNED. No remote work occurs in this transaction. Rollback leaves receipt unconsumed.
- Same-key original requests and identical same-purpose resubmissions recover the original immutable result under current authority. Other requests cannot bypass unique `(tenant,project,document_revision,purpose)` or one-use authentication constraints.
- Authorized history re-reads the genuine fixed document under current upstream/source permissions, checks persisted signed bytes byte-for-byte, checks manifest/registry/receipt/callback/operation/audit/outbox consistency, and never requires current policy/provider availability to read an old signature. A changed policy cannot alter signed bytes. External electronic signature/regulatory submission remain NOT_CONFIGURED.

## Contract and migration

`backend-design/document-signing-v1.openapi.yaml` and `business/medical-persistence/src/main/resources/document-signing-v1.schema.json` are additive. Old shared schema/catalogue digests are unchanged. Existing SignatureDetail fields are retained. BX16 inline history explicitly requires `X-Schema-Version: 1.1.0` and returns a closed inline SignatureHistory envelope, never a fake ArtifactRef. Other APIs use 1.0.0. No existing web signing calls were found, so no speculative frontend wiring was added.

Migration 140 adds immutable policies, independent approvals, current policy head, encrypted challenge bindings, genuine callback records, exact signed bytes and operation journal, plus real provenance FKs and immutable/one-way-consumption triggers. Parent owns master migration registration and coverage metadata. TaskPlanService adds only an additive `signing` gate that repeats its current formal execution checks for SIGN_PENDING; pre-existing modifications in that file are preserved.
